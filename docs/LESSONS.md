# Alert System — LESSONS

> 비자명한 교훈만 1줄로 상단 append. 자명한 요약 금지.

- 2026-08-10 **엔티티↔DDL 대조는 테이블 이름이 아니라 컬럼 단위로 해야 한다.**
  테스트는 SQLite + `synchronize=true`라 **엔티티에서 테이블을 만들어낸다** — DDL 파일에
  컬럼이 없다는 사실이 원리적으로 보이지 않는다. 프로덕션은 `synchronize=false`이고
  TypeORM은 선언된 모든 컬럼을 SELECT 목록에 넣으므로, 컬럼 하나가 없으면 그 엔티티를 쓰는
  기능 **전체**가 42703으로 죽는다. 지난 라운드들은 `CREATE TABLE` 개수만 대조해
  "누락 0건"을 보고했고, 그렇게 `users.phone_number`·`users.google_id`가 계속 통과했다.
  **테이블이 다 있다는 것은 아무것도 보장하지 않는다.**

- 2026-08-10 **요청을 무효화하는 가드는 로딩 플래그를 끌 책임까지 함께 없앤다.**
  abort/stale로 걸러진 응답은 `setIsSearching(false)`도 건너뛰므로, 뒤를 이어받는 이펙트가
  대신 꺼야 한다. 그런데 "검색할 게 없다"는 early return 경로가 플래그를 안 건드려
  두 검색 훅 모두 빈 입력창 위에 "검색 중..."을 영구히 남겼다. 게다가 에러·빈 상태가
  전부 `!isSearching`으로 가드돼 있어 **고착되면 재시도 버튼조차 못 나온다.**
  **무효화 가드를 넣을 때는 "그럼 이 플래그는 누가 끄나"를 early return까지 포함해 답한다.**

- 2026-08-10 **경계값 테스트를 실시간 시계로 만들면 "정확히 N일"을 만들 수 없다.**
  `new Date()`에서 30일을 뺀 뒤 `Date.now()`와 비교하면 그 사이 흐른 1ms 때문에
  30.0000000116이 되어 배타 경계(`> 30`)를 넘는다. 단독 실행은 빠르니 통과하고
  전체 스위트에서만 깨져 프로덕션 버그로 오인하기 쉽다.
  **경계 테스트는 `jest.setSystemTime`으로 시각을 고정하고 뺄셈도 그 고정값 기준으로 한다.**

- 2026-08-10 **테스트가 실패를 재현하는 방식이 환경에 의존하면 로컬 GREEN·CI RED로 갈린다.**
  `setupTests.ts`는 Node 25+의 깨진 built-in localStorage일 때만 자체 `MemoryStorage`로 대체한다.
  그래서 `vi.spyOn(window.localStorage, 'setItem')`은 로컬(Node 25)에서만 먹고 CI(Node 20)의
  jsdom Proxy Storage는 가로채지 못한다(`Storage.prototype` 스파이는 정반대로 갈린다).
  **저장 실패는 모듈 경계 mock 또는 `vi.stubGlobal('localStorage', ...)`로 재현한다.**

- 2026-08-10 **실패를 boolean으로 알려주는 래퍼는 호출부가 안 보면 없는 것만 못하다.**
  `safeSetItem`은 시크릿 모드·용량 초과를 false로 반환하도록 만들어졌는데 호출부 4곳 전부가
  무시해, Google 로그인이 "로그인 성공!"을 띄운 뒤 토큰 없이 이동해 로그인 화면으로 되튕겼다.
  **반환값을 쓰라고 만든 API는 도입 시점에 호출부 전수(grep)로 확인한다.**

- 2026-08-10 **배치 API는 한 건의 영구 실패로 큐 전체를 영원히 막을 수 있다.**
  `processBatch`가 이벤트별 try/catch 없이 던지는데 모바일은 업로드 실패 시 큐를 보존하므로,
  삭제된 장소를 참조하는 이벤트 하나가 오프라인 큐를 영구 정지시켰다(에러 표시도 없이).
  **클라이언트가 재시도하는 배치 엔드포인트는 건별 실패를 흡수하고 사유를 응답에 실어야 한다.**

- 2026-08-09 **자체 state로 목록을 들고 있는 화면은 캐시 미갱신 결함을 스스로 숨긴다.**
  `RouteSetupPage`는 저장 결과를 `existingRoutes`에 직접 넣어 그 화면에서는 멀쩡히 보이지만,
  홈·알림·설정이 읽는 react-query 캐시(routes **10분**, alerts 2분)는 손대지 않아 저장 직후
  홈에 그 경로가 없었다. **mutation 지점은 "이 화면이 맞게 보이나"가 아니라 "이 데이터를 읽는
  다른 화면의 캐시를 무효화했나"로 점검한다.** 같은 이유로 낙관적 토글도 로컬 state만 뒤집으면
  staleTime 안에 재방문 시 옛 값으로 되돌아간다 — 낙관적 업데이트에는 **성공 후 invalidate가 짝**이다.

- 2026-08-09 **`@IsNotEmpty`는 `''`만 막고 `'   '`는 통과시킨다.** 공백뿐인 값이 DTO를 지나
  도메인에서 trim 후 걸리면 그 예외는 500이 된다 — 검증은 **엔티티가 아니라 DTO에서, trim한
  뒤에** 끝내야 한다(`@Transform` 먼저, `@IsNotEmpty` 나중). 그리고 **개수 제한은 생성에만
  걸면 이동으로 뚫린다**: `createMission`이 유형별 3개를 막아도 `updateMission`의 타입 변경에
  같은 검사가 없으면 4개가 된다. 정원 검사는 "새로 만들 때"가 아니라 **"그 칸에 들어갈 때"**에 건다.

- 2026-08-09 **입력 검증을 bare `Error`로 던지면 검증이 장애로 둔갑한다.** `AllExceptionsFilter`가
  non-HttpException을 500 + 'Internal server error'로 덮으므로, 사용자는 한국어 사유를 못 받고
  서버는 정상 입력 오류를 `logger.error`+스택으로 쌓아 **진짜 장애를 가린다**. 그리고 서버가
  범위를 강제하면(경로 2~5개) 클라이언트도 같은 범위를 알아야 한다 — 하한만 지키고 상한을
  안 걸어서, 경로를 6개 이상 저장한 사용자만 비교 카드가 영구히 에러로 굳어 있었다.
  **범위 상수는 양쪽에 명시하고, 클라이언트는 "보내기 전에 서버 계약에 맞추는" 순수 함수를 둔다.**

- 2026-08-08 **서버 DTO를 좁힐 때는 그 엔드포인트를 부르는 클라이언트 페이로드를 실제로
  대조하라 — 그리고 이전 리뷰의 결함 서사도 검증 대상이다.** UpdateRouteDto를 신설하며
  체크포인트 id 수용은 테스트했지만, 프론트가 PATCH에 CreateRouteDto(userId 포함)를
  재사용하는 것은 아무도 대조하지 않아 forbidNonWhitelisted에 걸려 **경로 수정 자체가
  전면 400**이었다. 직전 리뷰는 "id 없는 PATCH가 성공하며 기록을 지우는 중"이라고
  적었지만 실제로는 400이라 도달조차 못 했다 — 결함 A를 고칠 때 그 주변 서사(B가
  일어나고 있다)는 재현 없이 믿지 말 것. 화이트리스트 파이프 아래서 DTO 계약 변경은
  "받는 쪽 spec"만으론 부족하고 보내는 쪽 페이로드 빌더를 순수 함수로 뽑아 같이 테스트해야 한다.

- 2026-08-07 **비율을 만들 때 분자와 분모를 다른 모집단에서 뽑으면, 넘칠 때가 아니라
  "정확히 100"을 보는 쪽에서 터진다.** 미션 달성률의 분모는 활성 미션, 분자는 그날의
  완료 기록 전부였다. 완료한 미션을 비활성화하면 150%가 되는데, 스트릭 판정이
  `completionRate === 100`이라 **초과하는 순간 스트릭이 0으로 리셋**됐다. 상한 클램프를
  걸었으면 150→100이 되어 이번엔 반대로 스트릭이 부당하게 이어졌을 것이다 —
  고칠 자리는 판정식이 아니라 **분자의 모집단**이다. 같은 파일의 화면 경로는 이미
  올바르게 세고 있었고 저장 경로만 틀렸다(2026-08-06 교훈의 재발). 두 경로가 같은
  함수를 쓰게 만들지 않으면 이 부류는 계속 나온다.

- 2026-08-07 **디바운스는 요청 수를 줄일 뿐 응답 순서를 정하지 않는다.** 역 검색이
  300ms 디바운스만 걸고 stale 가드가 없어, 먼저 보낸 "강남"의 응답이 "역삼"보다 늦게 오면
  입력창과 목록이 어긋났다. 더 눈에 띄는 건 두 번째 경로다 — 역을 고른 뒤 `clearSearch()`로
  비운 목록을, 떠 있던 요청이 도착해 **되살린다**. 결정적으로 같은 앱의 자매 훅
  (`use-transport-search`)은 `AbortController` 가드를 갖고 있었다: 같은 기능이 두 벌
  구현돼 있으면 결함은 "둘 다 없음"이 아니라 **"한쪽만 없음"** 으로 나타나므로,
  중복 구현을 발견하면 동작이 아니라 **가드의 유무를 대조**하는 게 가장 빠르다.

- 2026-08-06 **화면이 약속한 값과 저장되는 값을 각자 계산하면 반드시 갈라진다.**
  알림 마법사의 `generateSchedule`(저장)과 `getNotificationTimes`(미리보기)가 같은 루틴에서
  각자 시각을 계산했다. 크론의 분 필드는 모든 시각에 공통이라 저장 쪽은 분을 버리고
  `0 7,8,19 * * *`을 만들었는데, 미리보기는 분을 살려 `07:45`라고 표시했다 — **최대 59분 어긋난 알림**.
  둘 다 "맞는" 계산이라 어느 쪽 코드를 봐도 버그로 안 보이는 게 이 결함의 성질이다.
  약속과 실행이 나뉜 자리는 계산을 공유시켜(한쪽이 다른 쪽에서 값을 받아오게) 갈라질 여지를 없앤다.
  테스트도 값 하나를 박제하지 말고 "미리보기 시각 ∈ 크론 발화 시각"이라는 불변식을 검사한다.

- 2026-08-06 **계정을 여는 열쇠로 쓰는 값은 발급처가 소유를 확인해준 것만 받는다.**
  구글 로그인이 이메일로 기존 계정을 찾아 연동하는데(`findByEmail` → `updateGoogleId`),
  정작 `email_verified`를 한 번도 보지 않았고 이메일이 없으면 `''`로 `findByEmail('')`까지 갔다.
  OAuth 프로필의 필드는 "받은 값"이지 "검증된 값"이 아니다 — 연동 키로 쓸 거면 입구에서 끊는다.
  (남은 반대 방향: 가입 시 이메일 인증이 없으면 선점 연동은 여전히 가능 — 기능 결정 필요)

- 2026-08-06 **"브랜치는 이미 생성됨"을 믿지 말고 원격을 먼저 본다.**
  자동 리뷰 worktree의 로컬 HEAD가 7월 커밋으로 되돌아가 있는데(main 대비 39 behind)
  같은 이름의 원격 브랜치에는 열린 PR의 최신 작업이 있었다. 로컬 기준으로 push했으면 남의 커밋을 날린다.
  착수 시 `git ls-remote` + `gh pr list --head`로 원격 상태를 먼저 확인하고, 리셋이 아니라 그 위에 쌓는다.

- 2026-08-06 **"노출하지 않는다"를 주석으로 적으면 안 지켜지고, 문법으로 적으면 지켜진다.**
  `useAuth`가 localStorage 값 5개를 `join('|')` → `split('|')`으로 위치 재조립하면서
  `// parts[3] is accessToken -- skip (not exposed to components)` 주석으로 의도를 남겼다.
  이름은 `@MaxLength(50)`만 걸린 사용자 입력이라 `홍|길동`이면 필드가 한 칸 밀려
  `parts[4]`(phoneNumber)에 **accessToken이 들어오고 설정 화면에 JWT가 렌더**됐다.
  직렬화와 역직렬화가 짝이 아니면 그 틈은 항상 입력이 정한다 —
  구분자 join+split은 값 중 하나라도 사용자 입력이면 쓰지 말 것(JSON 인코딩).
  그리고 노출 금지 같은 규칙은 인덱스 주석이 아니라 구조 분해의 홀로 강제한다.

- 2026-08-04 **`parseInt('7-9')`는 NaN이 아니라 `7`이다.** 크론 시각 필드를
  `parseInt` + `isNaN` 필터로 훑던 파서가 범위 `7-9`를 "07시 단일 알림"으로 읽었다.
  결과는 두 갈래로 터졌다 — 중복 판정이 `0 7 * * *`와 같다고 보고 **07:00 알림 생성을
  영구 차단**했고(우회 불가), 수정 모달은 저장 때 범위를 조용히 지웠다.
  후자는 2026-08-02 교훈(`값 N개를 대표하는 입력 위젯`)과 같은 뿌리인데,
  **그때 만든 보호 장치를 파서의 오독이 통과시켜 버렸다** — 보존 로직을 고쳐도
  그 앞의 파서가 틀리면 무효다. `isNaN`은 숫자 검증이 아니다. `/^\d+$/`를 쓸 것.

- 2026-08-04 **검증 데코레이터가 하나도 없는 DTO는 "검증 안 함"이 아니라 "전 필드 거부"다.**
  `whitelist` + `forbidNonWhitelisted` 조합에서 데코레이터 없는 필드는 *비화이트리스트*로
  분류돼 `forbidNonWhitelisted`가 요청 전체를 400으로 반려한다. `BriefingQueryDto`가
  그랬고, 프론트는 항상 `?lat=&lng=`를 붙이므로 엔드포인트가 100% 죽어 있었다.
  ↑ 아래 08-04 교훈의 "**`@Query()`는 그물을 통과한다**"는 **부정확하다** — 그물을
  통과하는 건 `@Query('limit') s: string`처럼 **원시 타입**으로 받을 때뿐이고,
  DTO 클래스로 받으면 `@Query()`도 정상적으로 검증 대상이다. 즉 이 파이프 설정엔
  양면이 있다: 원시 타입은 무검증 통과, 무-데코레이터 DTO는 전면 거부.
  **그리고 어느 쪽도 컨트롤러 메서드를 직접 부르는 단위 테스트로는 재현되지 않는다** —
  파이프를 태우지 않기 때문이다. `design:paramtypes`로 선언된 metatype을 꺼내
  전역 파이프와 같은 설정으로 통과시켜 보는 것이 가장 싼 검증법이다.

- 2026-08-04 **전역 `ValidationPipe`는 `@Body()`만 검증한다 — `@Query()`는 그물을 통과한다.**
  그래서 컨트롤러 8곳이 `parseInt(x) || 기본값` + `Math.min(상한)` 관용구를 복사하며
  **하한 검증 부재를 함께 복제**했다. TypeORM은 음수 `take`/`skip`을 검증 없이
  `LIMIT -1`로 실어 보내고(better-sqlite3로 실측), **Postgres는 500, SQLite는 무제한**으로
  갈린다 — 즉 테스트 DB가 SQLite인 한 이 부류는 영원히 초록이다.
  쿼리 파라미터는 DTO를 안 거치므로 컨트롤러가 마지막 방어선이다.

- 2026-08-03 **자동 리뷰 브랜치는 날짜 기반이라, PR이 안 머지되면 같은 날 다음 라운드가
  같은 이름을 재사용한다.** 16:00 라운드 착수 시 `feature/e2e-auto-review-20260803`이
  이미 08:00 라운드의 **열린 PR #169의 head**였다. 관례대로 `origin/main`에 리셋하고
